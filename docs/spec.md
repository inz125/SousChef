## 6. 実装待ち

仕様は決まったが、まだ実装していない項目。受け入れ条件（Given/When/Then）と実装の注意点を、この仕様書だけを読んで実装を始められる粒度で書く。実装したら項目ごと消す（決定事項の D-xx は残す）。

### 6.1 レシート撮影による一括登録（D-06, D-42, MVP スコープ 5）

#### 受け入れ条件

1. **入口**
   - Given 在庫画面を開いている（オンライン）、Then ヘッダー右上の＋の左にカメラボタン（aria-label「レシートを読み込む」）がある
   - Given オフライン、Then カメラボタンは押せない（D-17。＋ボタンと同じ扱い）
   - When カメラボタンを押す、Then `<input type="file" accept="image/*">`（`capture` は付けない。iPhone では「写真を撮る / 写真ライブラリ / ファイルを選択」が出る）で 1 枚選べる。選ばずに閉じたら何も起きない
2. **読み取り中**
   - When 写真を選ぶ、Then 「レシートを読み取っています…」を表示し、読み取りが終わるまでカメラボタンと＋ボタンは押せない
3. **確認画面**（全画面のシート。見出し「レシートの食材」）
   - Then 読み取った食材が 1 行ずつ並ぶ。各行に: チェック（初期値 ON）、名前（テキスト入力）、カテゴリ（D-23 の 12 分類から選ぶ）、保存場所（D-10 の 4 区分から選ぶ）
   - 食品以外・割引・小計・税・レジ袋の行は出ない。レシートに同じ食材が複数行あっても 1 行にまとまる
   - 名前は一般名（例: 「ｺｸｻﾝﾄﾘﾑﾈ」→「鶏むね肉」、「ﾒｲｼﾞｵｲｼｲｷﾞｭｳﾆｭｳ」→「牛乳」）
   - カテゴリ・保存場所の初期値: 名前が補完候補（`food_catalog`）にあればその値、なければ AI の推定（例: 冷凍食品 → 冷凍、にんじん → 野菜室）
   - 名前を補完候補にある名前へ書き換えたら、カテゴリ・保存場所をその値に入れ直す（D-27 と同じ）
   - 名前が在庫の食材と完全一致する行には「在庫あり（「ある」に戻します）」と表示する（名前を書き換えたら判定し直す）
   - 下部に「キャンセル」と「登録する（N 件）」。N はチェックが ON の件数。0 件のとき、または ON の行に名前が空のものがあるときは「登録する」を押せない
4. **登録**
   - When 「登録する」、Then チェックが ON の行ごとに:
     - 在庫に同じ名前の食材がある → 新しい行を作らず、その在庫（同じ名前が複数あれば期限が近い順の先頭 1 件）を 量「ある」、期限を今日からの目安（D-24、カテゴリ・場所はその在庫のもの）・目安の印あり に更新する。カテゴリ・保存場所は変えない
     - ない → 量「ある」、期限は今日からの目安（D-24）・目安の印あり で追加する（補完候補には既存のトリガーで記録される）
   - Then 確認画面を閉じ、一覧に反映し、「N 件を在庫に登録しました」を 4 秒表示する
   - チェックが OFF の行は何もしない。「キャンセル」なら何も登録しない
   - もう一人への通知は既存の D-30 のとおり（追加・更新ごとに通知される。まとめる仕組みは作らない）
5. **読み取れなかったとき・エラー**（確認画面は開かず、在庫画面にメッセージを表示）
   - 食材が 1 つも読み取れない（レシートでない写真・食品なし） → 「食材を読み取れませんでした。レシート全体が写るように撮り直してください」
   - 1 日の上限（D-21、レシート 10 回）を超えた → 「今日のレシート読み取り回数の上限に達しました。明日また使えます」（上限判定はサーバ側。献立の回数とは別に数える）
   - AI が回答を断った → 「レシートを読み取れませんでした。撮り直してお試しください」
   - 通信・サーバの失敗 → 「レシートの読み取りに失敗しました。時間をおいてお試しください」

#### 実装の注意点

- **Edge Function** `read-receipt`（POST `/functions/v1/read-receipt`）。`suggest-meals` と同じ構成にする: 処理本体 `_shared/readReceiptHandler.ts`（DB と AI を差し替え可能）、Claude 呼び出し `_shared/claudeReceiptReader.ts`、DB `_shared/supabaseReceiptDeps.ts`、`read-receipt/index.ts` は組み立てだけ。CORS・401/403/429/422/502 の扱いも `suggestMealsHandler.ts` に揃える
- **リクエスト**: `{ image: string（base64、data: 接頭辞なし）, mediaType: 'image/jpeg' | 'image/png' | 'image/webp' }`。形が違う・base64 が 5MB を超える → 400「画像が正しくありません」
- **画像の縮小**: ブラウザで送る前に長辺 2000px 以下・JPEG（品質 0.85）に縮小する（iPhone の写真は大きく、Edge Function と API の上限を超えるため）。縮小は関数に切り出し、コンポーネントテストでは差し替える
- **写真は保存しない**: Supabase Storage は使わない（`config.toml` で無効のまま）。Edge Function もリクエスト中だけ扱う
- **上限**: `consume_ai_quota('receipt', 10)`。テスト用 Supabase では `RECEIPT_DAILY_LIMIT` で大きな値にする（`scripts/test-db.mjs`。`MEAL_DAILY_LIMIT` と同様）
- **Claude 呼び出し**: モデル `claude-sonnet-5-5`。画像は `image` コンテンツブロック（base64）で送り、構造化出力（zod スキーマ。`claudeSuggester.ts` と同じ `betaZodOutputFormat`）で受ける。effort は `medium`。拒否（`stop_reason === 'refusal'`）は `RefusedError`
- **応答スキーマ**: `{ items: { name: string（1 文字以上）, category: D-23 のキー, location: D-10 のキー }[] }`（最大 50 件）。zod で必ず検証する。カテゴリ・場所はモデルの出力を信用せずスキーマで弾き、名前は前後の空白を除いて空のものを捨てる。同じ名前が複数あればサーバ側でも 1 つにまとめる
- **プロンプトで伝えること**: 食材（飲料・調味料を含む食べ物）だけ。日用品・レジ袋・割引・小計・合計・税・ポイントは除外。略称・半角カナ・ブランド名・産地・容量を外した一般名にする。同じ食材は 1 つにまとめる。カテゴリの一覧（キーと日本語名）と保存場所の一覧、食材ごとに家庭での一般的な保存場所を推定すること
- **補完候補・在庫との照合は画面側**で行う（Edge Function は AI の結果だけ返す）。照合・登録内容の組み立ては純粋関数（例: `src/domain/receipt.ts` の `receiptDrafts(items, catalog)` と `receiptChanges(drafts, inventory, today)`）にして単体テストする。期限は `estimateExpiresOn`、在庫の選び方は `stockCandidates` の完全一致側を使う
- **画面からの呼び出し**: `MealsApi` と同様に `ReceiptApi` インターフェース＋ Fake ＋ Supabase 実装で切る。在庫の更新・追加は既存の `InventoryRepository` を使う
- **テスト**: モック Claude（`tests/support/mockClaude.ts`）にレシート用の固定応答（食材数件、補完候補にある名前・在庫にある名前を含む）を追加する。統合テストで上限（`kind = 'receipt'` が献立と別に数えられること）・未ログイン / 許可リスト外の拒否を確認する。E2E は小さなテスト画像を選んで、確認画面 → 1 件のチェックを外す → 登録 → 一覧に反映・既存の在庫が「ある」に戻る、を 1 本
- 完了したら D-22 の「実装済み」と「3. MVP スコープ」の 5 を更新する
