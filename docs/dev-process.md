# 開発プロセス

このドキュメント自体を開発対象として扱い、機能を 1 つ作るごとに振り返って更新する。

## 1. 基本サイクル（機能 1 つ分）

仕様を決める段階と実装する段階を分け、**仕様書を書いたところで一度止める**。段階ごとに使うモデルを利用者が切り替えられるようにするため（KPT #13）。

### 段階 A: 仕様（ここで止める）

1. **仕様確認**: `docs/spec.md` の該当 D-xx を確認。曖昧な点はインタビューで決めて D-xx として追記する
2. **受け入れ条件を書く**: `docs/spec.md` の「6. 実装待ち」に、ユーザー視点の振る舞い（Given/When/Then）と実装の注意点を書く。会話の文脈を知らない別のモデルが、仕様書だけを読んで実装を始められる粒度にする
3. **コミットして止める**: 仕様書だけをコミット・push し、PR を作って決めた内容を利用者に報告して**実装には進まない**。利用者が PR をマージし、実装の指示を出すまで待つ

### 段階 B: 実装（利用者の指示で始める）

1. **仕様を読む**: `docs/spec.md` の該当 D-xx と「6. 実装待ち」の受け入れ条件だけを根拠にする。足りない点があれば推測せず利用者に聞き、仕様書に追記する
2. **TDD**: 外側から内側へ
   - E2E（Playwright, iPhone ビューポート）で受け入れ条件を 1 本 Red にする
   - ドメインロジックを単体テスト（Vitest）で Red → Green → Refactor
   - UI コンポーネントを Testing Library で Red → Green → Refactor
   - Supabase との結合（RLS・Edge Functions）を統合テストで確認
   - E2E を Green にする
3. **品質ゲート**: コミット前に `npm run verify`（format / lint / typecheck / 単体・コンポーネント / 統合 / E2E / build）が成功すること。結果は終了コードで判断し、出力を grep した結果をコミットの条件にしない。CI（GitHub Actions）でも同じものを実行する。ただし CI はドキュメント（`docs/`・`*.md`）だけの変更では統合テスト・E2E と公開を省く（`scripts/ci-changes.mjs`）
4. **仕様書の後始末**: 実装した項目を「6. 実装待ち」から消す（決定事項の D-xx は残す）
5. **振り返り（KPT）**: 下の「改善履歴」に追記し、必要ならこのドキュメント・CLAUDE.md・CI・スクリプトを更新
6. **PR を作る**: 実装・後始末・KPT を 1 つの PR にして利用者に報告する。マージは利用者が行う

## 2. ローカル環境

```sh
npm ci
sudo dockerd &           # クラウドのコンテナでは Docker デーモンが起動していないので手動で起動
npm run db:start         # 開発用 Supabase（API :54321）。npm run dev はここに接続
npm run test:db:start    # テスト用 Supabase（API :54421）。初回はイメージ取得で数分
npm run check            # format / lint / typecheck / 単体・コンポーネントテスト
npm run test:integration # テスト用 Supabase に対する統合テスト
npm run test:e2e         # テスト用 Supabase に接続する開発サーバ（:5174, --mode test）を自動起動
```

- **開発用とテスト用の DB は分離している**。テスト用は `scripts/test-db.mjs` が `supabase/config.toml` からポートとプロジェクト名だけ変えた設定を `.test-supabase/` に生成して起動する（設定の元は 1 つ）
- テストのヘルパーはテスト用（:54421）以外の Supabase に接続しようとするとエラーで止まる
- テスト用 DB を空にしたいときは `npm run test:db:reset`（直後はリアルタイム機能の再起動に数秒かかる）
- 既存の DB には新しいマイグレーションが自動では適用されない。マイグレーションを追加したら reset する
- テストユーザーは共通のパスワード（`tests/support/supabase.ts` の `TEST_PASSWORD`）で作り、パスワードでログインする
- スキーマ変更は `supabase/migrations/` に SQL を追加し、`npx supabase db reset`（開発用）と `npm run test:db:reset`（テスト用）で反映
- プロセスを止めるときは `pkill -f` や `ps | grep` のパターンで探さない（実行中のシェル自身のコマンド行にも一致して止まる）。ポート番号から PID を特定する
- Edge Runtime は起動時に npm からパッケージを取得する。TLS を中継するプロキシの内側（クラウドの開発環境）では取得できないため、Deno 上の起動確認は CI に任せる

## 3. テスト方針

| 層             | ツール                                            | 対象                                                                | 方針                                                                                                                                                         |
| -------------- | ------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 単体           | Vitest                                            | ドメインロジック（期限推定、提案条件の組み立て、AI 応答の検証など） | 純粋関数として切り出し、最も厚く書く                                                                                                                         |
| コンポーネント | Vitest + Testing Library                          | 画面・部品の振る舞い                                                | ユーザー操作で検証。実装詳細に依存しない                                                                                                                     |
| 統合           | Vitest + Supabase ローカル（CLI）                 | RLS、Edge Functions、Realtime、Supabase 実装のアダプタ              | 新しいテーブルには「許可リスト外・未ログインは読み書きできない」テストを必ず書く                                                                             |
| E2E            | Playwright（iPhone ビューポート）                 | 主要動線                                                            | 少数精鋭。AI はモックサーバで固定応答                                                                                                                        |
| Edge Function  | Vitest（server プロジェクト）+ CI の Edge Runtime | 処理本体・Claude 呼び出し・Deno 上の起動                            | 処理本体は DB/AI を差し替えて単体テスト。Node 上で本物のテスト用 DB + モックの Claude で統合テスト。Deno 上の起動は CI（`EDGE_FUNCTIONS=1`）のスモークテスト |

- **AI（Claude API）**: 実 API はテストで呼ばない。プロンプト組み立てと応答スキーマ検証を単体テストし、SDK には偽の `fetch` を差し込んでリクエストの形を検証する。統合テスト・E2E は `tests/support/mockClaude.ts`（:54499）を Claude API として使う。応答は zod で必ず検証し、アレルギー除外のような安全上の条件はモデルの出力を信用せずサーバ側でも確認する
- **外部サービスの境界**: 認証など外部サービスはインターフェース（例: `AuthApi`）で切り、UI テストはインメモリの Fake、アダプタは統合テストで実物に対して検証する
- **失敗の理由まで検証する**: エラーになることだけでなく、エラーの種類（メッセージ）まで確認する。別の理由で失敗していても通ってしまうのを防ぐ
- **共有データ**: 1 世帯なのでログインした全員が同じデータを見る（変更通知も届く）。テスト用 DB は開発用と分離しているが、テスト同士では共有するので、テストで作るデータは名前に一意な値を含め、通知などは自分のデータに関する文言で確認する。E2E は干渉を避けるため 1 ワーカーで順に実行する
- **時刻**: 期限・日次上限などは「今日」を注入してテストする。単体テストは `TZ=Asia/Tokyo` で動かし、UTC とのずれによる日付バグを検出する

## 4. ブランチ・コミット・マージ

- **段階ごとに PR を作り、こまめに main へマージする**（継続的インテグレーション）。段階 A（仕様）と段階 B（実装）はそれぞれ 1 つの PR にする。ブランチを長く生かして複数の段階を溜めない
- **PR は自動で作る**。段階の終わり（仕様書の push、実装の push）に、利用者に聞かずに Claude が PR を作る
- **マージは利用者が行う**。Claude は PR を作り、CI が通ったことを確かめて報告するまで。Claude はマージしない
- 次の段階は、前の PR がマージされた最新の main からブランチを作り直して始める。マージ前の PR があるうちに別の段階を始めるときは、その PR に積まず、利用者に確認する
- 1 コミット = 1 つの意味のある変更（Red/Green/Refactor を細かく刻んでもよい）
- コミットメッセージは日本語可。先頭に種別（feat / test / fix / refactor / docs / chore / process）

#### #5 追記: CI の失敗 2 件

- **単体**: 「元に戻すは 5 秒後に消える」が CI でだけ失敗。単独実行では毎回失敗し、全体実行では通る＝実行順依存だった。原因は非同期処理後の state 更新が React の act の外で起き、タイマーを仕掛ける副作用が未実行のまま時間を進めていたこと。`findBy` で待つように修正
- **統合**: Realtime は起動直後、購読は成功しても数秒間イベントを配信しない。CI では起動直後に走るため最初のテストがタイムアウト。リアルタイムのコンテナを再起動して再現させ、「イベントが実際に届くまで待つ」準備処理を追加
- **製品側の改善**: 同じ種類の隙間（最初の読み込み〜購読開始の間の変更）を取りこぼさないよう、購読開始後に読み直すようにした
- **Try（実施済み）**: 単体テストを毎回ランダムな順で実行（`sequence.shuffle`）し、実行順依存を検出する
- **Try**: 失敗は「手元で再現 → 原因特定 → 修正 → 同条件で再確認」の順を守る（今回 2 件ともこの順で直せた）

### #6 献立提案（設定画面・Edge Function・献立画面）（2026-10-25）

- **Keep**: 型チェックをテストにもかけていたので、テストの条件オブジェクトの型の甘さに気づけた
- **Problem**: `ps | grep` でプロセスを止めて自分のシェルを止めた（#2 の pkill と同じ種類の失敗を繰り返した）
- **Problem**: 文字列置換・位置での切り貼りによる編集が、整形（prettier）後のコードと一致せず黙って失敗したり、ファイルを壊したりした
- **Problem**: 「別の場所に作って差し替える」並列対策が、コンテナのマウントを壊していた（前回の修正が今回の不具合の原因に）
- **Problem**: この環境の Edge Runtime が npm に接続できず、証明書の受け渡しを 2 通り試して時間を使った
- **Try（実施済み）**: プロセスはポート番号から特定する。置換で編集するときは一致を assert してから行い（今回のドキュメント更新でさっそく不一致を検出）、構造の大きな変更はファイルを書き直す
- **Try（実施済み）**: 環境依存で動かない検証は時間を区切り、検証方法を分けて（Node 上の統合テスト + CI のスモークテスト）明記する
- **Try**: テストで共有データに左右される箇所（世帯共通のアレルギーなど）は、件数でなく中身で確認する
- **Problem**: 失敗した E2E があるのにコミット・push した。テスト出力を grep した結果を `&&` でつないでいたため、失敗行に一致した grep が成功扱いになった
- **Problem**: その E2E の失敗は、長い食材名で画面が横にはみ出す本物の不具合だった（fieldset の既定の min-width）
- **Try（実施済み）**: `npm run verify` を追加し、終了コードで判断する。E2E に「横スクロールが出ない」確認を追加（モバイルでは innerWidth ではなく screen.width と比べる）
